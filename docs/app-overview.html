workflow-task · 客户端核心闭环

服务端下发 WorkflowConfig，客户端回传 outputSchema 结果

用户不点运行。后端按账号推送完整配置，本机走固定流程：校验 → Chrome 扩展执行 workflow → Agent 按 instruction 汇总 → 回传对齐 outputSchema 的 JSON。 执行日志另传 OSS，地址写在回包的 clientLogOssUrl。下面以「携程 EBK 评论回复」为例。

01 后端

下发 WorkflowConfig

workflow + instruction + outputSchema。metrics 键在此时定死。

02 校验

三件套齐全才跑

缺字段就停，不臆造格式。

03 扩展

只跑 workflow

打开 EBK、听包、点回复。不管怎么汇总。

04 Agent

按 instruction 处理

只填 outputSchema.metrics 已有的键。

05 定稿

对齐 outputSchema

成功、失败、需要登录都用同一骨架。

06 回传

JSON + 日志地址

结果入库做报表；clientLogOssUrl 留给排障。

一份配置，三种角色

Chrome 扩展

workflow / maxRetry

去哪个页、点哪个按钮、听哪条接口。instruction 不进扩展。

本机 Agent

instruction

自然语言：回复待回复评论，再按 metrics 模板统计。不加戏、不增字段。

回传后端

outputSchema

最终 JSON 合同。信封（时间、成败、日志）+ 下发时定死的 metrics。

场景：携程 EBK 评论回复

后端下发完整配置，不是让客户端自己想。metrics 有哪些键，写在下发的 outputSchema.metrics 里；客户端只按样填值。

后端收什么

    

      后端只收对齐 outputSchema 的 JSON。业务报表用信封 + metrics；排障用 clientLogOssUrl。
      原始抓取数据和 workflow 细节留在客户端，不上报。
      失败（含需要登录）也要传日志，否则最难查的情况没有现场。
    

    

      
        
交给后端不上报

      
      
        

          outputSchema 结果（含 metrics、errorCode、时间、日志地址）
          Chrome 采集到的原始 payload / Cookie / 评论原文
        

        

          执行日志（OSS）里的进度与错误摘要
          商家密码、验证码；WorkflowConfig 全文（后端自己有）
        

      
    

    
OSS 上传失败时：业务 JSON 照交，clientLogOssUrl 为 null，可带 logUploadError。


    
回传字段：公共信封 + 下发时定死的 metrics

    

      metrics 的字段名由任务下发时的 outputSchema.metrics 定死。
      客户端只填值，不准增删键。后端用自己保存的 schema 解析。
      信封（时间、成败、日志地址）是客户端协议固定槽，建议写在同一份 outputSchema 模板里。
    

    

      
        
字段含义谁定 / 谁填

      
      
        
taskId后端业务任务 ID下发时带上，原样带回

        
platform / platformLabel枚举如 ctrip / meituan / douyin；展示名如「携程EBK」下发时带上

        
taskType如 review_reply、order_summary下发时带上

        
ok / needsLogin是否跑完；是否因登录态失效而停客户端填

        
errorCode / error机器可判的失败码；给人看的原因。成功为 null客户端填

        
startedAt / finishedAt / durationMs开始、结束、耗时客户端填

        
clientVersion客户端版本客户端填

        
clientLogOssUrl执行日志 OSS 地址客户端填；上传失败为 null

        
metrics.*本任务业务结果键由下发 schema 定死；客户端填值，失败则 0 / null / []

      
    


    
errorCode

    

      
        
码含义客户端侧

      
      
        
LOGIN_REQUIRED商家后台未登录或会话过期引导去 Chrome 登录；metrics 全 0

        
EXTENSION_DISCONNECTED扩展未连接提示打开 Chrome 并加载扩展

        
CRAWL_FAILEDworkflow 执行失败看 OSS 日志，不编数据

        
AGENT_FAILED抓取成功但汇总失败看 Agent 日志

        
CANCELLED用户停止或后端取消不重试除非再下发

        
CONFIG_INVALID下发配置不完整后端修配置

      
    


    

      约定
      扩展只执行 workflow。instruction / outputSchema 只在顶层，不当步骤字段。
      抓取失败立刻停，不编造 metrics。成功才按 instruction 填下发模板里的键。
      无论成败，先上传执行日志，再把 clientLogOssUrl 写进回包。日志不含 Cookie 和接口原文。
    

  


  

  

  

    
账号系统 · 多端登录与任务投递

    
只给装了扩展的客户端下发任务

    

      看数据：只装客户端。跑任务：客户端 + Chrome 扩展。
      后端不按账号广播，只看「这个账号下哪些设备扩展在线」。0 台 → 提示安装；1 台 → 打给它；≥2 台 → 取第一台，用户不用选。

        跑任务

        两台都装了

投递规则

    

      
        
该账号下，扩展当前在线的设备数行为

      
      
        

          0
          任务保持 WAITING_EXTENSION。所有已登录的客户端提示：「请在一台电脑上安装并打开浏览器扩展」。不让用户挑机器。
        

        

          1
          任务只推到这台。另一台没装扩展，收不到。
        

        

          ≥2
          按 extensionBoundAt ASC 取第一台，只 push 给它。其余有扩展的设备也不跑这一单。
        

      
    

    

      「第一台」= 这个账号下第一次上报扩展在线的设备，时间写下 extensionBoundAt，之后不再改。
      投递时再滤掉当前不在线的；在线集合里仍然按这个时间取最早。不要用心跳新旧、商家 Cookie、打分。

实现上只需卡住这几件事

    

      
        
点做法

      
      
        

          不要按账号广播
          任务 push 到选中的 deviceId。没扩展的客户端连这条通道都没有。
        

        

          taskId 单飞
          Task.assigneeDeviceId 写下第一台。回传带 deviceId；重复上报丢弃。防止两台扩展同时在线时的竞态。
        

        

          第一台离线
          它不在「当前扩展在线」集合里。若还剩别的扩展在线，取集合里 boundAt 最早的（可能变成原来的第二台）。若一个都不在线 → 走 0 台提示。
        

        

          卸扩展 / 重装客户端
          扩展断开则该设备离开候选。重装客户端会得到新 deviceId，extensionBoundAt 是新的，排序上变成「更晚的一台」。
        

        

          商家没登录
          跟调度无关。任务已经打到第一台，由那台回 LOGIN_REQUIRED，引导在这台 Chrome 登录。不要因为 Cookie 再换一台。
        

      
    


    

      约定
      不跑任务 = 不装扩展。调度只认扩展在线列表：0 提示，1 投它，多台投第一台（extensionBoundAt 最早）。
      用户不选执行端。商家登录仍在被选中的那台 Chrome 里完成。
    

  


  

  

  

    
酒店上下文 · 绑定 + 运行时核对

    
平台酒店 ID 安装时绑一次，之后任务按这份下发

    

      后端一开始不知道携程/美团的酒店 ID。这个 ID 只存在商家后台的登录态里。
      所以安装向导里要有「绑定酒店」：点按钮，扩展去当前 Chrome 读出平台酒店 ID，客户端保存并同步后端。没绑定就不下发该平台任务。
      绑定不是每次跑任务再选一次店；跑的时候只拿这份 ID 和当前页面核对，防串店。
    


    
安装时：绑定平台酒店

    

      

        
01

        
装客户端 + 扩展

        
只装客户端看报表；要跑任务才装扩展。绑定按钮依赖扩展。

      

      

        
02

        
Chrome 登录商家后台

        
和平时一样。先把顶栏切到「就是要抓的那家店」，再点绑定。

      

      

        
03

        
点「绑定酒店」

        
扩展读当前店（同一套「我是谁」探测）。弹出店名 + platformHotelId，确认后写入。

      

      

        
04

        
本地保存 + 上报后端

        
只存在客户端，后端第一次下发仍然没有 ID。两边都有了才允许投任务。

      

    


    

      

        
绑定成功后写入的记录

        

      

      

        
按钮在做什么

        
不是让用户手填 ID，也不是酒店下拉。读的就是现在 Chrome 里开着的那家。

        
确认文案必须带店名和平台 ID，避免同名店绑错。绑错了再切顶栏、再点一次覆盖。一个平台可以绑多家：切到下一家再绑，后端按 platformHotelId 存多条。

      

    


    

      
        
状态后端客户端

      
      
        

          该平台一条绑定都没有
          不下发该平台任务
          安装未完成 / 商家连接页提示去绑定。和「没装扩展」同一类门闩。
        

        

          已绑定
          任务 targetHotel.platformHotelId 用这份
          本地缓存同值，开跑前和当前 Chrome 比对。
        

        

          重装客户端
          绑定还在账号下
          登录后拉下来，不必再绑。除非用户要改店。
        

      
    


    
跑任务时：只核对，不再选店

    

      

        
01 下发

        
targetHotel 写进配置

        
用绑定得到的 platformHotelId。客户端不准另猜一家。

      

      

        
02 开跑前

        
读出当前店，比对

        
从页面或「我是谁」接口拿 currentHotelId。不等指令去「感觉」。

      

      

        
03 不一致

        
停，不采、不写

        
回 HOTEL_MISMATCH。metrics 全 0。提示去商家后台切到目标店。

      

      

        
04 跑的过程中

        
每条包校验酒店 ID

        
用户中途切店 → HOTEL_SWITCHED，已采数据丢弃，不当成功回传。

      

    


    
不要做的三件事

    

      

        反模式
        
信当前页面

        
打开评论页就开始听包。当前是哪家店完全取决于用户上次点了什么。

      

      

        反模式
        
每次任务再选酒店

        
和已绑定、已下发的 ID 容易选叉。选店只发生在安装绑定；任务里没有酒店下拉。

      

      

        默认不要
        
静默帮用户切店

        
EBK 的当前酒店通常是整段登录态，不是单个标签。采集窗口里一切，用户正在看的页面也会变。

      

    


    
配置里必须有目标酒店

    

      

        
WorkflowConfig 增加的字段

        

      

      

        
错店时回传（同一骨架）

        

      

    

    

      platformHotelId 来自绑定，不是运营手填。必须是商家后台那个 ID。我们库里的 hotelId 可以后补关联，但不能代替平台 ID——扩展在页面里对得上的只有平台 ID。
    


    
当前酒店从哪读

    

      
        
来源用途

      
      
        

          开跑前：平台「当前酒店」接口或顶栏 DOM
          决定能不能开始。读不到等同于上下文不明，停，不要当匹配。
        

        

          采集到的每个请求/响应里的酒店字段
          决定这条数据能不能进本单。缺字段的包：能从会话上下文推断则用开跑时的 ID，推断不了就丢这条。
        

        

          酒店切换接口 / 顶栏点击
          跑的过程中一旦出现，立即 abort，不要等这一步 workflow 跑完。
        

      
    


    
三种现场

    

      
      
      
    

    


    
errorCode

    

      
        
码何时客户端

      
      
        

          HOTEL_UNBOUND
          该平台还没有绑定记录（或任务里缺 platformHotelId）
          不下发；已在客户端则提示去点「绑定酒店」。不是跑起来再猜。
        

        

          HOTEL_MISMATCH
          开跑前 current ≠ 已绑定/已下发的 target
          不采。提示：当前是「A」，本单要「B」，请在商家后台切换。不要让用户在客户端改绑定来「迁就」当前页，除非他确认绑错了要重绑。
        

        

          HOTEL_SWITCHED
          已经开始后 current 变了，或某条采集的酒店 ID 对不上
          丢弃本单已采数据。不把 A+B 混成一份 metrics。
        

        

          HOTEL_NOT_ACCESSIBLE
          这套商家登录里根本没有目标酒店（读酒店列表对不上）
          不是切一下能解决。提示换有权限的账号在 Chrome 登录。
        

        

          HOTEL_UNKNOWN
          登录着，但读不出当前酒店 ID
          当失败，不要降级成「先抓了再说」。
        

      
    


    
和登录提示同一类交互

    

      绑定、登录、切店都是「去 Chrome 做一件商家后台里本来就会的事」。
      客户端只有两个按钮级动作：绑定酒店（安装/改绑）和登录失效时的「去浏览器登录」。任务执行过程中没有酒店下拉。
    

    

      
        
登录失效酒店不对

      
      
        

          扩展发现跳到登录页 / 401
          扩展发现 currentHotelId ≠ targetHotel.platformHotelId
        

        

          提示去 Chrome 完成登录
          提示去 Chrome 切到「XX酒店」（带平台 ID，避免同名店）
        

        

          回 LOGIN_REQUIRED，metrics 为 0
          回 HOTEL_MISMATCH，metrics 为 0
        

      
    


    

      为什么默认不自动切店
      采集可以开独立窗口，但商家后台的「当前酒店」多半写在 Cookie / 全局 header 里，一切就是整次会话都切。
      用户正在看 A 店订单，任务要 B 店，静默切换等于抢走他的工作台。
      若某平台列表接口可以在 body 里带 hotelId、不依赖顶栏当前店，优先走 call_api 带目标 ID，根本不用动 UI。这是平台适配，不是账号协议。
    


    
Agent 侧

    

      
        
点规则

      
      
        

          开跑前失败
          和抓取失败一样：不跑 instruction，不编 metrics。
        

        

          采集结果里混了别的店
          扩展应在听包阶段就丢掉或直接 abort。Agent 不得「尽量汇总还能用的」。
        

        

          回传信封
          带上 targetHotel 与 actualHotelId（读到的当前店），方便后端对账，不进业务报表数字。
        

      
    


    

      约定
      平台酒店 ID 靠安装时「绑定酒店」从 Chrome 读出，写入客户端并同步后端；未绑定不下发。
      之后任务带这份 ID。扩展开跑前、采集中核对，对不上就停。绑是一次性身份，选店不进任务界面。
